Modernizing QA: from manual sign-off to an automated pipeline

The QA workflow on the Boost website is a chain of manual steps performed by one person. This is a plan to remove the human from the mechanical links of that chain — and to shape the result into a QA practice Metalab can carry to the next client.

The reframe

When a PM says “automation,” they don’t mean a specific tool — they mean an outcome: “I shouldn’t have to wait on one person clicking through every PR, and I want to see that a change works without asking someone.” The complaint is that QA sits in the critical path as a human bottleneck, and that the proof a change works is a person’s hand-pasted screenshots — which don’t scale, aren’t repeatable, and stall the moment that person is out.

With the added context that Metalab is continually improving QA for its clients — through new tools, AI, and automation — this stops being a one-off fix and becomes a capability. The deliverable is a repeatable QA pattern the studio can demonstrate and reuse, piloted here because Boost already has most of the plumbing.

01 — Current state

The QA chain today

Every link except the deploy engine itself is a person. Mapping it end to end shows exactly where the toil lives — and why “it’s too manual” is a fair complaint.

STEP 01
Decide a PR needs QA
Coordinated over Slack or verbally. Nothing on the PR records that a preview was requested.
👤 Manual
STEP 02
Get the PR onto staging
QA runs scripts/deploy-qa.sh locally, which force-pushes the PR’s commit onto the cppal-dev branch of the QA fork.
👤 Manual
STEP 03

The push triggers CI-GCP: build the image, helm upgrade into the cppal-dev namespace, purge the CDN. This is the one automated link.
⚙ Automated
STEP 04

A person opens cppal-dev.boost.cppalliance.org and clicks through the flow in light mode, dark mode, and mobile.
👤 Manual
STEP 05

Screenshots are captured by hand and pasted into the PR’s ## Screenshots grid — the labor the team keeps seeing (PRs #2482, #2475, #2481).
👤 Manual

👤 Manual

02 — Interpretation

What “automation” most plausibly means

The trap is that an engineer hears “automation” and builds a clever test suite, while the PM’s daily pain is waiting on a person to press a button. Ranked by how likely each is the real ask:

1

Self-serve, PR-triggered previews most likely

A preview comes up from the PR itself — a label or a button — with the URL posted back, no named person running a laptop script. Removes steps 01–03 and takes QA out of the gate. The biggest, most PM-shaped lever.

2

Automated evidence instead of hand-pasted screenshots

Screenshots across light/dark/mobile generate themselves in CI and land on the PR, so proof-of-working isn’t an artifact a human assembles by hand. This is the visible symptom the team keeps pointing at.

3

An automated pass / fail signal

Not just pictures — a check that goes red when a change breaks a page, so nobody has to interpret a screenshot. The leap from “here’s what it looks like” to “the system says it’s good.”

4

The whole loop, hands-off

Open PR → deploy → verify → post results → set status → release the slot, with a human only for judgment calls. The aspiration — steps 01–07 automated — even if #1 is the immediate ask.

03 — The team’s own taxonomy

Three levers: tools, AI, automation

The team named the categories themselves. Here is what each realistically buys against the chain above — and, for AI, an honest split between what works today and what only demos well.

Automation

DETERMINISTIC

The boring, reliable core. Highest ROI — do this first.

  • PR-triggered preview deploy (removes the human-as-gate)
  • Auto-captured screenshots + visual-regression check posted to the PR
  • Auto-run of the changed flows on the live preview

New tools

ENABLERS

The layer that makes the automation possible — and gives the practice a name to point at.

  • Playwright — already in requirements.txt (1.58), Chromium already wired in CI. E2E + built-in toHaveScreenshot() visual diffing.
  • Baseline snapshots so “did the UI change?” is a reviewable diff, not a human comparison.

AI

ACCELERANT

New and marketable — but keep it assisting the deterministic checks, not replacing them.

Useful today
  • Draft the per-PR test plan from the diff + description
  • Vision-model review of screenshots (cut-off, contrast, overflow)
  • Triage a red run: real regression vs. flaky selector
Handle with caution
  • Fully autonomous “self-healing” agents that decide pass/fail with no baseline — flaky, and a sign-off nobody can reproduce
04 — Where people see it

The GitHub-native experience

No custom dashboard. The whole thing is one sticky comment, a couple of checks, and a small label set — each tuned to a different reader, in the team's priority order: QA operates it, the developer fixes from it, the PM glances at it.

①

QA Engineer the operator

The entire interaction is adding the qa label. The automation owns the rest and reports into a single sticky comment that updates in place — no thread spam. She clicks the preview for human judgment, glances at the visual report, signs off.

Intentional UI changes are resolved with a comment command that updates the stored baseline so the check goes green — QA owns this: /qa approve-baseline

Developer the fixer

Failures arrive as checks right on the PR, each actionable, and the sticky comment flips to point at what and where. Click a diff, fix, push — checks re-run automatically on the new commit. They never leave the PR.

05 — Phased pilot

A roadmap that stays demonstrable at every step

Sequence matters. Phases 1–2 remove the toil and each demos on its own; phase 3 is the differentiator Metalab can market — but bolting AI on before the deterministic base exists just yields unreliable magic.

PHASE 1

Deploy automation

removes steps 01–03
What

A PR-triggered workflow (a qa label is the recommended trigger) does what deploy-qa.sh does, server-side, and comments the preview URL back on the PR. Keeps the single shared cppal-dev slot.

Why first

Immediate relief, smallest change, and it directly answers the “why does this depend on one person?” complaint. Needs one new thing: a cross-repo push credential.

PHASE 2

Verification automation

removes steps 04–06
What

Playwright drives the changed pages across light / dark / mobile, captures screenshots, diffs them against a committed baseline, and posts the images + a pass/fail check to the PR.

Payoff

The ## Screenshots grid fills itself and the check becomes a real regression gate — not a vibe check. Uses tooling already in the repo.

PHASE 3

AI layer

assists steps 04–06
What

An LLM drafts the test plan from the PR diff/description and triages failures; optional vision-model review covers the “matches Figma / a11y” checklist items.

Positioning

The differentiator for the Metalab QA offering: AI writes and triages the tests; automation runs them deterministically; the tools do the diffing and reporting.

06 — Before we build

Two things to confirm with the team

  • Where’s the real pain? Is it “it’s too slow/manual to get a preview up” (→ ship Phase 1 now) or “I don’t trust hand-pasted screenshots as proof” (→ lead with Phase 2/3)? Same components, different first deliverable — the one ambiguity the code can’t resolve.
  • Boost fix, or Metalab offering? A “make Boost’s QA less painful” mandate means ship Phases 1–2 as-is. A “build the studio’s QA capability” mandate means design Phases 2–3 for portability from day one, so it drops onto the next client.
